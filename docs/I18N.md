# Traductions

Les messages sont embarqués dans `src/client/src/design-system/i18n/messages/`.
**Ajouter une langue = ajouter un fichier** `<code>.json` (par ex. `de.json`) :
elle apparaît automatiquement dans le sélecteur de langue.

1. Copier `fr.json` (langue de référence) vers `<code>.json`.
2. Traduire les valeurs ; renseigner `language.name` (nom affiché, dans la langue)
   et `language.direction` (`ltr`, ou `rtl` pour l'arabe, l'hébreu…).
3. Garder les variables à l'identique (`{count}`, `{label}`…).
4. Pluriels : une valeur objet par catégorie de `Intl.PluralRules` de la langue
   (`zero`, `one`, `two`, `few`, `many`, `other`), `other` étant obligatoire.
5. `npm run test:client` : un test vérifie que chaque langue contient toutes les
   clés du français avec les mêmes variables.

Dans le code : `const { t } = useI18n();` puis `t('clé')`,
`t('clé', { variable })` ou `t('clé', 'texte de repli')`. Une clé absente
retombe sur le français, puis sur le texte de repli.

État actuel : la navigation, la barre supérieure, l'arbre, les Paramètres et
tous les écrans métier sont traduits (français, anglais).

Garde-fou : `node scripts/check-i18n-hardcoded.js` audite l'arbre syntaxique
de tous les fichiers du client **et du site vitrine** (`site/src`), et signale
les textes affichés en dur. Seuls sont exclus les fichiers dont les chaînes
ne sont pas de l'habillage d'interface (données par défaut modifiables par
l'utilisateur, messages de développement). Le même code est exécuté par le
test `src/client/src/design-system/i18n/hardcoded-text.test.js`, qui échoue si
un texte en dur réapparaît, dans le client comme dans le site.

`node scripts/check-i18n-keys.js` vérifie que chaque clé utilisée existe en
français et en anglais, et que le texte de repli est identique à la valeur
française. Il audite également `site/src` : le site est une application React
séparée qui réutilise le design system via l'alias `@design-system`, donc le
même catalogue de messages et le même hook `useTranslation`.

## Clés dynamiques

Une clé peut être passée à `t(...)` par variable, quand elle est stockée dans
un tableau puis rendue plus tard :

```jsx
const FEATURES = [
  { key: 'local', title: 'site.feature.local.title', text: 'site.feature.local.text' },
];
// …
<h2>{t(feature.title)}</h2>
```

L'appel `t(feature.title)` n'apparaît pas comme une clé littérale dans
l'arbre syntaxique : l'audit des appels `t(...)` ne le voit pas. Pour couvrir
ce cas, `check-i18n-keys.js` recense dans les fichiers du site tous les
littéraux qui ressemblent à une clé de traduction (motif
`^[a-z][a-zA-Z0-9]*(\.[a-zA-Z0-9]+)+$`) et vérifie leur présence en français
et en anglais. Les sources d'import, les valeurs d'attributs JSX (noms de
classes, identifiants) et les premières arguments d'un appel `t(...)` littéral
sont écartés pour ne pas produire de faux positif.

En pratique : toute clé destinée à être traduite doit exister dans
`messages/fr` **et** `messages/en`, qu'elle soit écrite
`t('site.badge', '…')` ou stockée dans un tableau.
